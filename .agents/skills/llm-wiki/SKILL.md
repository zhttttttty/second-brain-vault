# LLM Wiki

让 `03_Knowledge/` 成为会随来源和问题持续更新的知识层，而不是静态笔记集合。人负责选择来源、提出问题和确认判断；AI 负责查重、比较、交叉链接、更新综合理解、维护索引和记录变更。

## 不变量

- 先读 `System/Vault_Schema.md`、`03_Knowledge/INDEX.md`、相关 Topic/MOC 和最近的 `03_Knowledge/CHANGELOG.md`。
- `04_References/` 中的来源正文是证据层。捕获后不改写正文；知识修订写到卡片或 Topic。移动或删除来源必须单独确认。
- 优先更新已有页面，只有达到建卡门槛时才创建新页。
- 区分来源主张、AI 推断和用户结论；重要结论保留可点击来源。
- 默认只读分析。创建、修改、移动或删除文件前，先展示影响范围并获得明确授权。
- 每次已授权的知识写回都同步更新 `03_Knowledge/INDEX.md`，并在 `03_Knowledge/CHANGELOG.md` 记录一次操作。

## 模式一：Ingest

当用户要求“摄取、整合、编译、纳入 Wiki”一个或多个来源时使用。

1. **确定来源**：读取用户指定的本地文件或已捕获剪藏。URL 尚未捕获时先使用 `capture-web`。不要把无法读取的链接当作已读来源。
2. **构建影响图**：提炼核心主张、证据、边界和关键实体；说明内容未来服务的判断、行动或创作场景；搜索已有卡片、Topic、项目与其他来源，标记重复、补充、冲突和空白。
3. **提出整合计划**：列出准备创建或更新的页面、关键改动、链接变化、INDEX 条目和来源处置建议。小来源允许结论为“不创建内容”。
4. **确认后执行**：
   - 更新已有卡片中的事实、边界、来源或质量信号；
   - 只为独立且可复用的新概念创建卡片；
   - 对适用模板填写 1～3 个具体 `use_when` 调用场景，不把场景混入主题标签；
   - 更新相关 Topic 的“当前理解”，而不只是追加链接；
   - 建立少量有明确语义的交叉链接；
   - 更新 INDEX 中受影响页面的一句话说明、来源数和更新时间；
   - 在 CHANGELOG 写一条 `ingest` 记录。
5. **验证**：检查 Frontmatter、Wikilink、重复文件名和来源链接；结构变化后运行 Vault 校验。

多个来源只有在用户明确给出批量范围时才批量处理。批量时先跨来源去重，再统一更新页面，避免同一页面被反复改写。

## 模式二：Query

当用户要求“根据我的知识库回答、比较、连接、综合”时使用。

1. 先从 `03_Knowledge/INDEX.md` 定位页面，再对卡片、Topic、References、Projects 和必要的 Daily Notes 做聚焦搜索。
2. 回答中用 `[[内部页面]]` 标明 Vault 依据；外部事实使用来源 URL。明确区分已有知识、综合推断和仍缺证据的部分。
3. 如果答案形成了可重复使用的新比较、框架、连接或阶段性综合，提出一个最小写回方案：
   - 优先更新现有 Topic；
   - 单一稳定观点才创建卡片；
   - 有完成标准的行动进入项目或任务，而不是知识页。
4. 只有用户确认后才写回。写回后更新 INDEX，并在 CHANGELOG 写一条 `query` 记录。

普通答案、一次性建议、证据不足的猜测和聊天过程不应写回。

## 与现有技能的分工

- `capture-web`：把公开网页可靠捕获到 Inbox，不负责知识整合。
- `digest`：一次处理一篇剪藏，帮助用户判断价值与去向；经确认的长期知识可转入本技能的 Ingest 模式。
- `card-creator`：已明确只需创建或更新一张原子卡片时使用。
- `knowledge-system`：需要六步法提炼模型或搭建领域体系时使用。
- `check-health`：检查矛盾、失效链接、孤立页面和标签；不替代 Ingest 或 Query。

## CHANGELOG 格式

在当天日期下追加一条，保持最新日期在上：

```markdown
- `ingest` | 整合《来源标题》，更新 N 个页面 | [[页面一]]、[[页面二]]
- `query` | 将“问题”综合结果写回 Topic | [[主题页面]]
```

没有实际文件写回时不记录 `ingest` 或 `query`。
